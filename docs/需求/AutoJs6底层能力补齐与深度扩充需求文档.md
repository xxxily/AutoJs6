# AutoJs6 底层能力补齐与深度扩充需求文档

> 状态: 需求分析稿
> 日期: 2026-06-08
> 范围: 面向 AutoJs6 的底层自动化能力、运行时能力、工程保障和生态扩展能力补齐
> 目标: 将 AutoJs6 从“功能丰富的脚本自动化工具”推进为“可稳定感知、可靠执行、可观测、可扩展、可治理的 Android 自动化平台”

## 1. 背景与结论

AutoJs6 当前已经不是一个轻量脚本壳。当前项目已经具备较完整的 Android 自动化基础: JavaScript/Rhino 运行时、无障碍自动化、选择器、手势、截图、图像处理、OCR、多后端定时任务、项目打包、插件中心、Shizuku/Root/Shell 能力、内置文档、代码编辑器、日志、AI 脚本助手一期等。

因此后续“深度扩充能力”的重点不应是继续堆单点 API, 而应优先补齐以下底层平台能力:

- 能力状态中心: 把权限、服务状态、设备兼容、脚本声明和运行前检查统一起来。
- 可靠自动化引擎: 把“找到控件并点击”提升为带等待、重试、稳定性评分、快照、回退和诊断的执行系统。
- 屏幕感知管线: 把截图、OCR、图像识别、无障碍树统一为可复用的屏幕理解能力。
- 特权能力结构化: 将 Shizuku/Root 从 shell 字符串通道升级为安全、可审计、可声明的结构化 API。
- 任务执行可靠性: 为定时任务、后台运行、失败恢复、并发控制、运行记录补齐可观测和调度语义。
- API/文档/补全/AI 索引一致性: 建立运行时 API 的源头索引, 避免文档、补全、AI 使用过期能力。
- 插件生态治理: 在已有插件中心基础上补 SDK、权限声明、签名索引、诊断和插件能力发现。
- 测试与兼容实验室: 为无障碍、截图、OCR、定时、Shizuku、打包建立设备级回归保障。

## 2. 当前项目事实依据

以下事实来自当前仓库扫描, 后续需求应优先复用现有实现, 避免重复造基础设施:

- 项目是 Android/Kotlin/Java 多模块工程, app 当前版本为 `6.7.2`, 主 app 目标 SDK 已到 36, `MIN_SDK_VERSION` 为 24, `inrt` 目标 SDK 为 29。
- `AndroidManifest.xml` 已声明极宽的能力面, 包括存储/all-files、安装/卸载包、精确闹钟、网络、悬浮窗、电池优化、开机启动、通知、前台服务、media projection、Shizuku、短信/联系人/电话/相机/录音/位置/蓝牙/NFC 等。
- `ScriptRuntime.kt` 注入了大量脚本 API: `app`、`autojs`、`automator`、`barcode`、`base64`、`canvas`、`colors`、`console`、`device`、`dialogs`、`engines`、`events`、`files`、`floaty`、`http`、`images`、`ocr`、`plugins`、`recorder`、`selector`、`sensors`、`shell`、`shizuku`、`sqlite`、`storages`、`tasks`、`threads`、`timers`、`ui`、`web`、`zip` 等。
- 内置文档位于 `app/src/main/assets-app/docs/*.html`, AI 能力索引已经能解析这些 HTML 文档。
- `app/src/main/assets-app/indices/all.json` 存在明显陈旧点: `automator` 和 `selector` 仍指向 `widgets-based-automation.html`, 大量属性 URL 为空, 而实际文档已有 `automator.html`、`uiSelectorType.html` 等新文件。
- AI 脚本助手已经有供应商配置、OpenAI 兼容客户端、结构化输出、文档检索、风险检测、预览应用和文件管理器入口。现阶段主要缺口在索引可靠性、补丁质量、运行验证、隐私审计和更强上下文。
- `TimedTaskScheduler.kt` 已有 AlarmManager、WorkManager、android-job 后端, 并有精确闹钟配额和周期检查策略。
- 插件中心已有官方索引拉取、ETag 缓存、退避、签名指纹信任、用户授权、安装动作和启用状态管理。
- Shizuku 已有状态、权限、服务绑定、自动重连、shell exec、当前包名/Activity/组件查询, 但 UserService 主要仍是 shell 通道。
- 截图链路已经处理 Android 14 media projection 前台服务时序, `ScreenCapturer` 已有方向变化监听、独立 ImageReader 回调线程、超时、自愈和重建逻辑。
- OCR 已支持 MLKit、Rapid、Paddle 插件/内嵌引擎, 但仍缺统一引擎选择、性能画像、准确率诊断和连续识别管线。
- 无障碍与选择器能力很宽, 已有 `UiSelector`、`UiObject`、全局动作、手势、布局检查器等, 但缺少面向复杂自动化流程的稳定交互规划层。
- 常规 `src/test`/`src/androidTest` 文件搜索未发现测试文件, app 仅配置基础 JUnit/Android 测试依赖。对底层能力继续扩充前, 测试和设备回归是明显短板。

## 3. 分析原则

1. 先补平台能力, 再补单点 API。单点 API 越多, 如果没有状态检查、诊断和测试, 用户脚本会更难稳定。
2. 优先补“能让已有能力可靠起来”的能力。例如能力预检、运行记录、选择器稳定性、截图会话管理、索引一致性。
3. 对高权限能力做结构化和审计。Root/Shizuku/Shell 不应只作为字符串命令暴露给用户和 AI。
4. 文档、补全、AI、脚本运行时应共享同一份能力图谱。否则 AI 和编辑器会继续提示过期 API。
5. 以 Android 新版本限制为边界设计。目标 SDK 36、精确闹钟、前台服务、media projection、包可见性、后台启动、存储权限都会持续收紧。
6. 把工程保障当成底层能力。没有测试、基准和兼容矩阵, 自动化平台很难长期扩张。

## 4. 评估维度

### 4.1 努力程度

| 等级 | 说明 | 典型周期 |
| --- | --- | --- |
| S | 小范围改造, 主要是索引、文档、轻量 API 或 UI 串联 | 1-5 天 |
| M | 涉及一个核心模块, 需要数据结构、UI、测试或兼容处理 | 1-3 周 |
| L | 涉及跨模块架构, 需要运行时、UI、存储、测试共同改造 | 1-2 月 |
| XL | 平台级能力, 需要长期演进、设备实验和生态协作 | 2-6 月 |

### 4.2 回报等级

| 等级 | 说明 |
| --- | --- |
| 高 | 明显提升用户脚本成功率、可扩展性、安全性或 AI 生成质量 |
| 中 | 提升体验、效率或生态质量, 但不直接决定核心自动化成功率 |
| 低 | 属于锦上添花或依赖其他能力成熟后才释放价值 |

### 4.3 优先级

| 优先级 | 说明 |
| --- | --- |
| P0 | 深度扩充前必须先做或同步做, 否则后续能力会不稳 |
| P1 | 高价值主线能力, 应进入近期路线图 |
| P2 | 有明确价值, 但依赖 P0/P1 或工程量较大 |
| P3 | 长期生态或高级场景能力 |

## 6. 详细需求

### A1. 统一能力状态中心与运行前预检

当前状态:

- 权限能力分散在 `permission/*`、抽屉权限项、运行时 API、项目打包权限选择中。
- Manifest 已声明大量权限, 但脚本调用某 API 前无法系统知道“还缺哪些能力”。
- `auto.state`、`shizuku.state` 等已有局部状态, 但没有统一能力图谱。

需求:

- 新增 `capabilities` 运行时模块和 Android 侧能力注册表。
- 每个能力定义包含: 能力 ID、显示名称、关联 API、所需权限、所需服务、是否危险、检测函数、请求/跳转函数、降级方案、最小 Android 版本、inrt 支持情况。
- 支持脚本调用:
  - `capabilities.check(["accessibility", "screen_capture", "shizuku"])`
  - `capabilities.ensure(["accessibility"], { request: true, timeout: 10000 })`
  - `capabilities.explain("images.captureScreen")`
- 编辑器运行前可根据脚本静态扫描和 `project.json` 能力清单提示缺失项。
- AI 生成脚本时使用同一份能力注册表输出 requirements/risks, 避免只靠关键词猜测。
- 主 UI 提供“能力状态面板”, 显示无障碍、截图、悬浮窗、通知、Shizuku、Root、精确闹钟、电池优化、存储等状态。

验收标准:

- 至少覆盖 20 个核心能力: 无障碍、截图、悬浮窗、通知、存储、网络、Root、Shizuku、Shell、UsageStats、WriteSettings、WriteSecureSettings、精确闹钟、后台运行、电池优化、开机启动、安装 APK、卸载 APK、短信、联系人、相机、录音、定位。
- 对每个能力可返回 `available/requestable/missing/blocked/unsupported` 状态。
- 一个需要截图和无障碍的脚本, 运行前能准确提示缺失截图授权和无障碍服务。

评估:

| 努力 | 回报 | 优先级 | 依赖 |
| --- | --- | --- | --- |
| M | 高 | P0 | 权限模块、ScriptRuntime 注入、AI 索引 |

### A2. API/文档/补全/AI 索引一致性

当前状态:

- `assets-app/docs` 已覆盖大量模块。
- `AiCapabilityIndex` 已从 HTML 文档解析能力片段。
- `assets-app/indices/all.json` 存在旧链接和空 URL, 例如 `automator`、`selector`。

需求:

- 建立单一能力索引生成器, 输出:
  - 文档导航索引。
  - 编辑器补全索引。
  - AI 能力索引。
  - 风险/权限映射索引。
- 索引来源优先级:
  1. 运行时 `augment` 暴露函数和 `@ScriptInterface`。
  2. 文档 front matter 或结构化注释。
  3. 手工补充的能力元数据。
- 增加 CI 校验:
  - 文档文件存在。
  - URL anchor 存在。
  - 运行时导出的 API 至少在索引中可见。
  - 废弃 API 有明确标记。
- 修复 `all.json` 中旧的 `widgets-based-automation.html` 指向和空 URL。

验收标准:

- `automator`、`selector`、`images`、`ocr`、`shizuku`、`tasks` 等核心模块索引可跳转到实际文档。
- CI 能发现空 URL、坏 anchor、重复 key、运行时存在但索引缺失的 API。
- AI 生成使用不存在 API 的比例显著下降, 未命中时能明确提示“当前版本未发现该 API”。

评估:

| 努力 | 回报 | 优先级 | 依赖 |
| --- | --- | --- | --- |
| S-M | 高 | P0 | docs、runtime/api/augment、AI 助手 |

### A3. 可靠自动化执行 DSL

当前状态:

- 已有 `UiSelector`、`UiObject`、全局点击/滑动/手势、`auto.waitFor()`。
- 用户仍需要手写大量等待、重试、兜底和错误处理。
- 复杂 App 的 UI 动态变化、列表滚动、弹窗、遮挡、异步加载会导致脚本不稳定。

需求:

- 新增可靠交互 DSL:
  - `auto.waitUntil(condition, options)`
  - `auto.retry(action, options)`
  - `auto.stableClick(selector, options)`
  - `auto.stableSetText(selector, text, options)`
  - `auto.findWithScroll(selector, scrollContainer, options)`
  - `auto.dismissKnownPopups(rules)`
  - `auto.transaction(steps, rollback)`
- 每个动作返回结构化结果: 成功/失败、耗时、匹配控件、使用的 selector、失败原因、截图/树快照引用。
- 支持等待 UI 稳定: 连续 N 次树结构或 bounds 不变才执行点击。
- 支持点击前校验: 控件存在、可见、可点击、未被遮挡、中心点在屏幕内。
- 支持失败策略: 重试、滚动查找、改用坐标、改用父节点、改用 OCR 文字点击、放弃并输出诊断。

验收标准:

- 对常见“打开 App -> 等待首页 -> 搜索 -> 输入 -> 点击结果”的流程, 样例脚本可不写裸 sleep。
- 每次失败能给出可读的失败原因, 而不是只返回 false 或抛出泛化异常。
- 自动化 DSL 可被 AI 脚本助手优先使用, 降低生成脚本中的脆弱 sleep 和裸点击。

评估:

| 努力 | 回报 | 优先级 | 依赖 |
| --- | --- | --- | --- |
| L | 高 | P0 | A1、A4、A15 |

### A4. UI 树快照、差异与选择器评分

当前状态:

- 无障碍树和 `UiObject` 能访问控件属性。
- 有布局检查器和代码生成基础。
- 缺少面向运行期诊断、回放和 AI 上下文的标准快照格式。

需求:

- 定义 UI 快照格式:
  - 时间戳、包名、Activity、窗口列表。
  - 节点树: text、desc、id、className、bounds、clickable、enabled、depth、index、drawingOrder 等。
  - 脱敏策略: 可选隐藏输入框、手机号、邮箱等敏感文本。
- 支持 `auto.snapshot(options)` 导出 JSON。
- 支持 `auto.diffSnapshot(before, after)`。
- 为 selector 增加稳定性评分:
  - `id`/resourceName 权重。
  - text/desc 易变性。
  - bounds/index 脆弱性。
  - 匹配唯一性。
  - 跨多次快照稳定程度。
- 布局检查器和录制器生成代码时优先输出高评分 selector。

验收标准:

- 用户可在一次失败后导出 UI 快照, 供调试或 AI 修复使用。
- 同一控件多次快照能给出稳定 selector 建议。
- 录制器生成脚本中的选择器质量可量化展示。

评估:

| 努力 | 回报 | 优先级 | 依赖 |
| --- | --- | --- | --- |
| M-L | 高 | P1 | A1、A3、A12 |

### A5. 屏幕感知管线: OCR + CV + 无障碍融合

当前状态:

- 已有截图、OpenCV 图像处理、找图找色、OCR 多引擎。
- 这些能力多以独立 API 暴露, 脚本作者需要自行组合。

需求:

- 新增 `vision` 或 `perception` 模块, 将屏幕识别统一为对象列表:
  - 无障碍节点。
  - OCR 文本块。
  - 图像匹配结果。
  - 颜色/区域特征。
  - 当前 App/Activity。
- 支持区域感知:
  - `vision.observe({ region, interval, sources })`
  - `vision.findText("确定", { source: "ocr+a11y" })`
  - `vision.findButton("登录")`
  - `vision.waitForScene(sceneDefinition)`
- 支持多源融合:
  - OCR 识别到文字但无障碍树无节点时, 可用 OCR bounds 点击。
  - 无障碍节点无 text 但图像模板命中时, 可结合 bounds 定位。
  - 同一目标多来源命中时, 返回置信度和解释。
- 支持场景描述和复用:
  - “登录页”、“首页”、“支付确认页”可定义成 JSON/YAML 规则。

验收标准:

- 在无障碍节点缺失或文本不可见时, 样例脚本可通过 OCR/CV 兜底定位目标。
- 对同一屏幕可输出融合后的目标列表, 每个目标含来源、置信度、bounds、建议动作。
- 性能可控: 默认感知管线不造成明显卡顿, 支持采样频率和源开关。

评估:

| 努力 | 回报 | 优先级 | 依赖 |
| --- | --- | --- | --- |
| L-XL | 高 | P1 | A4、A6、A15 |

### A6. 截图会话管理和性能基准

当前状态:

- `ScreenCaptureRequester` 和 `ScreenCapturer` 已处理授权、前台服务、方向、超时、自愈。
- 但脚本层仍偏向单次 `captureScreen`, 缺少长期 session、帧缓存、性能画像。

需求:

- 新增截图 Session:
  - `images.openCaptureSession(options)`
  - `session.latest()`
  - `session.nextFrame(timeout)`
  - `session.close()`
- 支持帧缓存和生命周期管理, 防止脚本忘记释放 Image 导致资源耗尽。
- 支持按用途预设:
  - 单次截图。
  - 连续 OCR。
  - 高频找色。
  - 低功耗后台监测。
- 增加基准指标:
  - 首帧耗时。
  - 平均帧耗时。
  - 超时率。
  - 方向切换恢复耗时。
  - 内存占用。
- 将截图错误分类: 未授权、服务未启动、无帧、方向不匹配、ImageReader 异常、MediaProjection 失效。

验收标准:

- 连续截图 10 分钟不会明显泄漏或卡死。
- 方向切换后 session 能恢复并输出恢复事件。

## 7. 推荐路线图

### 7.1 0-1 个月: 先稳住能力图谱和可观测性

目标: 不急着加大能力面, 先让已有能力“知道自己有什么、缺什么、哪里失败”。

建议任务:

1. 修复 `assets-app/indices/all.json` 中 `automator`、`selector` 等陈旧链接和空 URL。
2. 建立 API/文档/AI 索引校验脚本。
3. 设计并落地第一版能力注册表, 覆盖核心权限和服务状态。
4. 为定时任务增加最小运行记录: 计划时间、触发时间、执行状态、异常。
5. 为 AI 助手接入真实能力索引, 改善未知 API 和高风险 API 校验。
6. 建立第一批 JVM 测试: ProjectConfig、AI result parser、索引校验、能力映射。

### 7.2 1-3 个月: 可靠自动化主线

目标: 将 AutoJs6 的核心竞争力从“能操作”提升为“稳定操作”。

建议任务:

1. 实现 UI 快照格式和导出能力。
2. 实现 selector 稳定性评分和布局检查器建议。
3. 实现 `auto.waitUntil`、`auto.retry`、`auto.stableClick`、`auto.findWithScroll`。
4. 为截图增加 Session API 和错误分类。
5. 任务调度增加重试、互斥、超时和运行历史 UI。
6. AI 二期支持补丁级应用和运行前预检。

### 7.3 3-6 个月: 屏幕感知和特权 API 平台化

目标: 让脚本具备跨 App、跨 UI 技术栈的感知和操作能力。

建议任务:

1. 实现 OCR+CV+无障碍融合的 `vision`/`perception` 第一版。
2. 建立场景规则格式和 `vision.waitForScene`。
3. 实现 Shizuku 结构化 API 第一批: app、settings、package、input。
4. 建立高风险调用审计日志。
5. 打包/inrt 接入能力清单和首次启动预检。
6. 建立设备兼容矩阵和核心基准报告。

### 7.4 6-12 个月: 生态、远程调试和多设备能力

目标: 将 AutoJs6 推进到平台生态阶段。

建议任务:

1. 插件 manifest、签名索引、SDK 模板和插件诊断。
2. 远程调试协议、运行时间线、日志流和诊断包导出。
3. 自动化方案库和 AI 检索增强。
4. 多设备任务编排和远程执行。
5. 更强脚本沙箱、网络/文件策略、插件隔离。

## 9. 高风险事项

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| Android 新版本限制持续收紧 | 后台运行、截图、权限申请、精确闹钟可能失效 | 能力中心记录版本差异, 建立设备矩阵 |
| 高权限能力滥用 | 用户隐私、安全和分发风险 | 能力清单、二次确认、审计日志、默认最小权限 |
| AI 生成危险脚本 | 用户误执行高风险操作 | 真实能力索引、风险检测、运行前预检、不自动运行 |
| 插件供应链风险 | 恶意插件或被篡改 APK | 签名索引、sha256 校验、权限声明、用户授权 |
| 自动化 DSL 过度抽象 | 用户难以理解失败原因 | 每个动作输出结构化诊断和原始底层信息 |
| 测试不足 | 底层扩充引入回归 | 先补 P0 测试和可控样例 App |

## 10. 非目标

以下事项不建议作为近期主线:

- 不建议优先做云端账号、团队协作、脚本商店等非底层能力。
- 不建议把 AI 设计成可直接控制手机的自动执行代理, 至少在能力清单、审计、确认机制成熟前不做。
- 不建议继续无约束增加危险权限 API, 应先建立能力声明和审计。
- 不建议单独追求 OCR/图像算法数量, 应先统一感知管线和性能基准。
- 不建议把插件中心做成开放市场后再补供应链安全, 安全模型应先行。

## 11. 需求实施依赖图

建议依赖顺序:

1. A2 API/文档/补全/AI 索引一致性。
2. A1 统一能力状态中心。
3. A15 测试与设备基准基础。
4. A8 任务运行记录和调度可观测性。
5. A4 UI 快照与 selector 评分。
6. A3 可靠自动化 DSL。
7. A6 截图 Session。
8. A12 AI Copilot 二期。
9. A7 Shizuku/Root 结构化 API。
10. A5 屏幕感知融合。
11. A9 安全沙箱与能力清单。
12. A10/A11/A13/A14/A16 生态、调试、数据、打包和方案库。

## 12. 第一阶段建议验收清单

第一阶段完成后, AutoJs6 应至少达到:

- 运行时核心 API、内置文档、补全索引、AI 索引不再互相漂移。
- 用户运行脚本前能看到缺失能力和可跳转的授权入口。
- 定时任务失败后能看到真实运行记录和失败原因。
- AI 生成脚本会基于真实能力图谱声明权限和风险。
- 一个复杂 UI 自动化示例不再依赖大量裸 `sleep`, 而是使用可靠等待和稳定点击。
- 失败诊断包至少包含: 日志、异常、能力状态、UI 快照、可选截图。

## 13. 总体建议

AutoJs6 最应该补的不是“更多权限”或“更多单函数”, 而是自动化平台的四个底座:

1. 能力图谱: 知道自己有什么、缺什么、能否请求、风险多高。
2. 可靠执行: 让控件选择、等待、点击、截图、OCR 变成可诊断的稳定动作。
3. 可观测治理: 每次运行、调度、特权调用、插件调用都能记录、解释和回放。
4. 工程保障: 用测试、基准和设备矩阵保证底层扩充不会反复破坏核心能力。

按这个路线扩充, AutoJs6 才能从“高级脚本工具”升级为“可靠 Android 自动化平台”。
